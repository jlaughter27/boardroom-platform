# OmniMind's Memory Bundle Is Unique; Its Front Door Isn't

**BLUF.** No product on the market today ships what OmniMind already has as one bundle: bi-temporal validity with `asOf` queries, supersede-with-provenance, hybrid retrieval that includes trigram matching, client-supplied `Idempotency-Key`, per-agent scoped keys, first-class decision/commitment/task/person/project entities, cron-driven cortex artifacts (memos, contradiction alerts, reflection capsules) and a built-in graph UI. The closest single competitor is Zep Cloud (bi-temporal, provenance, graph explorer, OAuth MCP) and it is SaaS-only from $125/month with no decision or task objects; the closest open-source analogue, Graphiti MCP, is labelled experimental, ships with no auth and carried a CVSS 8.1 Cypher-injection CVE this year ([Zep pricing](https://www.getzep.com/pricing/), [Graphiti MCP README](https://github.com/getzep/graphiti/tree/main/mcp_server), [CVE-2026-32247](https://cvefeed.io/vuln/detail/CVE-2026-32247)). But the *distribution layer* is fully commoditized: the official registry lists 265 unique "memory" servers, 103 of them remote, most pitching "one memory, every AI" ([MCP registry](https://registry.modelcontextprotocol.io/v0/servers?search=memory)). Our weakness is exactly there. The shipped `omnimind-mcp` server binds one agent identity per process from env vars, so one HTTP URL cannot distinguish two users; it has no OAuth; it speaks the 2025-11-25 protocol while the current spec (2026-07-28) removed sessions and deprecated the Dynamic Client Registration flow our Phase 10 roadmap is built around ([our_codebase_inventory.md](mcp-landscape-2026-10-11/notes/our_codebase_inventory.md), [MCP 2026-07-28 changelog](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/changelog.mdx)). The single most important blind spot: "stay up to date" via push does not exist in any major chat client; freshness is achieved by tool calls at turn time, so the planned `notifications/resources/updated` work should be demoted. On the graph, the next leap is wiring the already-shipped hybrid search into a spotlight-and-dim interaction and making the local graph the default, not a WebGL renderer swap. The verdict: keep building; the moat is the entity model, governance and cortex, and the next six weeks should go to OAuth with three registration paths, a ChatGPT `search`/`fetch` pair, and search-driven graph UX.

## Six blind spots the inventory and roadmap do not surface

The research exposes six issues that a founder reading only the roadmap would miss, and they matter more than any feature gap.

**First, the protocol moved under Phase 10.** The current MCP specification became 2026-07-28 on its target date; it removed `initialize` and `Mcp-Session-Id`, replaced `resources/subscribe` and the GET notification stream with a single `subscriptions/listen` stream, requires `Mcp-Method`/`Mcp-Name` headers on every POST, and formally deprecates RFC 7591 Dynamic Client Registration in favor of Client ID Metadata Documents ([MCP blog](https://blog.modelcontextprotocol.io/posts/2026-07-28/), [changelog](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/changelog.mdx)). Phase 10 is written as "OAuth 2.1 + PKCE + Dynamic Client Registration via WorkOS or Ory Hydra" with DCR as the long pole ([PHASE-10 README](docs/roadmap/04-roadmap/PHASE-10-mcp-server/README.md)). DCR is still needed for Cursor, Gemini CLI, Raycast and Copilot Studio, but Claude.ai and Claude Code now prefer CIMD and Anthropic recommends it over dynamic registration, so the ADR-014 provider spike must require all three paths: CIMD, DCR and pre-registered static clients ([Claude Code MCP docs](https://code.claude.com/docs/en/mcp), [Anthropic custom connectors help](https://support.claude.com/en/articles/11175166-getting-started-with-custom-connectors-using-remote-mcp)). Phase 10 also pre-dates the standalone package: its tool names (`searchMemories`, `createMemory`) and resource URIs (`memory://`, `entity://`) conflict with the shipped `memory_search`, `memory_write` and `omnimind://{tenant}/…` ([our_codebase_inventory.md](mcp-landscape-2026-10-11/notes/our_codebase_inventory.md)). Treat Phase 10 as partially superseded: transport, 18 tools, resources and prompts are done; OAuth, tenant-isolation eval and directory submission remain.

**Second, push-based freshness is a mirage.** Roadmap task 10.9 plans resources "with `notifications/resources/updated` support" ([tasks-and-prompts.md](docs/roadmap/04-roadmap/PHASE-10-mcp-server/tasks-and-prompts.md)). The protocol has that primitive, but it is a lightweight "re-read this URI" signal with no durability, no replay and no delivery guarantee, and the only shipping client evidence of honoring any update stream is Claude Code holding a `list_changed` stream open on 2026-07-28 connections; a 2025-10 third-party test found no major client auto-reads resources at all ([subscriptions spec](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/basic/patterns/subscriptions.mdx), [Claude Code MCP docs](https://code.claude.com/docs/en/mcp), [DollhouseMCP report](https://glama.ai/mcp/servers/@DollhouseMCP/DollhouseMCP/blob/62c9b46e851b3753b28f2b916e6379c465abb9d3/docs/development/MCP_RESOURCES_SUPPORT_RESEARCH_2025-10-16.md)). No notification turns into an assistant turn. "All platforms stay up to date" therefore means: one store, every client reads it at the start of relevant turns because the server's `instructions` and a cheap always-called tool make it do so. The event bus in Phase 12 is the real mechanism for agents and UIs *you* control, not for Claude.ai or ChatGPT.

**Third, the HTTP transport is single-identity.** Agent name, tenant, scopes and source weight come from `OMNIMIND_MCP_AGENT_NAME`, `OMNIMIND_MCP_TENANT_ID`, `OMNIMIND_MCP_SCOPES` at process start, and inbound auth is one static bearer compared constant-time ([our_codebase_inventory.md](mcp-landscape-2026-10-11/notes/our_codebase_inventory.md), `packages/omnimind-mcp/src/lib/auth.ts`, `src/transports/http.ts`). Every client connecting to one URL is the same agent in the same tenant with the same scopes. That is fine for one founder running one ChatGPT config today; it is the opposite of "one server for all platforms." Token-to-principal resolution is the work, not transport.

**Fourth, the richest search is reachable only from MCP.** `POST /memories/search` (hybrid, `asOf`, tags, status, cursor to 50) is wired through the BoardRoom server and `api.ts`, but the Memory Explorer still exposes only `q`/domain/class/status/sort, the ⌘K palette searches in-memory store slices (goals, projects, people, decisions) with no memory, task or commitment search, and the graph page has its own in-memory node search ([our_codebase_inventory.md](mcp-landscape-2026-10-11/notes/our_codebase_inventory.md), `MemorySearch.tsx`, `CommandPalette.tsx`). Time travel via `asOf` is a feature no competitor surfaces in a UI and ours is not surfaced either. Known limitation 10 compounds this: tasks and commitments are not searched by the context assembler ([.claude/CLAUDE.md](.claude/CLAUDE.md)).

**Fifth, the graph has zero render tests and a 200-memory cap.** Only `graph-data.test.ts` (three cases) covers the client graph; `KnowledgeGraphView`, `GraphPage`, `GraphControls`, `NodeInspector` and `UnlinkedMentionsPanel` are untested, the page fetches `memoryLimit: 200` against a server max of 500, `GET /graph` has no pagination, depth or cursor, there is no edge-type filter, and the legacy SVG `RelationshipGraph` still ships on the People page and dashboard ([our_codebase_inventory.md](mcp-landscape-2026-10-11/notes/our_codebase_inventory.md)). Bitemporal data exists server-side and the UI has no timeline.

**Sixth, our own quality margin is thin and documented.** The CI retrieval eval passed with for-persona recall@10 of 0.520 against a 0.5 gate and the `update` slice at recall@10 0.27 ([.claude/CLAUDE.md](.claude/CLAUDE.md) Known Limitations item 11). That is honest and better than any vendor's self-reported LoCoMo number, but it means "far more searchable" is partly a retrieval problem, not only a UI problem. Smaller drift items also need fixing: `chatgpt-desktop.json` and the smoke tests describe a `/health` payload the code does not return, PHASE-6-CONTRACTS describes an idempotency scope the middleware does not use, and CLAUDE.md says contradiction alerts run Tuesday 9pm while `cortex-config.ts` says Monday 04:00 ([our_codebase_inventory.md](mcp-landscape-2026-10-11/notes/our_codebase_inventory.md)).

## No competitor ships the bundle, but three ship better front doors

The field splits into three camps: hosted-first vendors with a remote Streamable HTTP endpoint behind OAuth or an API key (Zep, Supermemory, Mem0 cloud, Honcho, Hindsight Cloud), open-source engines whose MCP server is a self-run process with little or no auth (Graphiti, Cognee, Basic Memory, doobidoo, MemMachine), and frameworks that are not cross-client memory servers at all (LangMem dormant since October 2025, Mastra, memU, Letta after its March 2026 pivot to git-backed MemFS) ([Letta "Our Next Phase"](https://www.letta.com/blog/our-next-phase/), [LangMem PyPI](https://pypi.org/project/langmem/)). Pricing has converged on a free tier and a $19–$20 entry plan (Mem0 Starter $19, Supermemory Pro $19, Letta Pro $20, Basic Memory Cloud $15–19) with Zep the outlier at $125 Flex and $375 Flex Plus ([Mem0 pricing](https://mem0.ai/pricing), [Supermemory pricing](https://supermemory.ai/pricing/), [Zep pricing](https://www.getzep.com/pricing/)); several of these figures come from search excerpts of vendor pages that could not be fetched directly, so verify before quoting externally.

On data model, **only Zep/Graphiti has a true bi-temporal model** with `valid_at`/`invalid_at` plus `created_at`/`expired_at` and episode-level provenance ("the old fact stays in the graph with its timestamps") ([Zep temporal KG](https://www.getzep.com/ai-agents/temporal-knowledge-graph/), [Graphiti README](https://github.com/getzep/graphiti)). Supermemory has expiry plus a version chain, but its v5 API removes direct memory-write and version routes; Mem0's new algorithm is explicitly ADD-only with "no UPDATE/DELETE. Memories accumulate; nothing is overwritten" ([Supermemory v5 migration](https://supermemory.ai/docs/migration/api-v5-memory-forgetting), [Mem0 README](https://github.com/mem0ai/mem0)). Hybrid lexical-plus-vector retrieval is table stakes (Graphiti, Honcho, Hindsight, Basic Memory, MemOS), **nobody documents trigram or fuzzy matching, no vendor documents an `Idempotency-Key` for writes, and no product has first-class decision, commitment or task objects with lifecycles** ([Hindsight README](https://github.com/vectorize-io/hindsight), [Honcho README](https://github.com/plastic-labs/honcho), [Cloudflare Agent Memory dedup](https://developers.cloudflare.com/agent-memory/concepts/how-agent-memory-works/)). Scheduled intelligence exists in pieces (Supermemory "Dynamic Dreaming", Honcho `schedule_dream`, Hindsight background consolidation with webhooks) but no one ships weekly memos or contradiction *alerts* as persisted, user-facing objects ([Supermemory dreaming](https://supermemory.ai/blog/introducing-dynamic-dreaming-supermemory-now-connects-the-dots-for-you/), [Honcho MCP](https://github.com/plastic-labs/honcho/tree/main/mcp)). A 2026 survey still calls contradiction checking "a necessary quality gate but still underdeveloped" ([arXiv 2603.07670](https://arxiv.org/pdf/2603.07670)).

Where competitors are plainly ahead is the front door. Zep's Memory MCP requires OAuth 2.1 with PKCE, gives each user only their own memory by default, and lists Claude, Claude Cowork, ChatGPT and Cursor ([Zep connect docs](https://help.getzep.com/memory-mcp-server/connect), [Zep launch post](https://blog.getzep.com/agent-memory-mcp)). Supermemory's OAuth consent screen lets the user pick read-only versus read-write and full versus scoped "spaces" per client, which is the only product answer found to the community question "which memories may each tool see" ([Supermemory ChatGPT setup](https://supermemory.ai/docs/supermemory-mcp/chatgpt-web)). Hindsight (MIT, self-hostable, 48.3k stars as rendered on GitHub and not cross-checked) runs recall as four parallel strategies merged with RRF plus a cross-encoder, isolates "banks" strictly, and issues bank-scoped child API keys whose revocation cascades ([Hindsight README](https://github.com/vectorize-io/hindsight), [Hindsight API keys](https://docs.hindsight.vectorize.io/api-keys/)). In the PKM world, Notion's hosted MCP is the only mainstream tool every client can reach with vendor-run semantic search and typed databases, but it is OAuth-only with no headless service accounts, has no graph, and reportedly returns 429s without back-off under agent load ([makenotion README](https://github.com/makenotion/notion-mcp-server), [Stacklok guide](https://docs.stacklok.com/toolhive/guides-mcp/notion-remote)). Obsidian has the best graph UX and still no first-party MCP; its reference Local REST API plugin now serves 2026-07-28 and sessionful revisions but requires the desktop app running, and forum evidence puts the graph's practical ceiling near 10–25k notes ([Local REST API](https://github.com/coddingtonbear/obsidian-local-rest-api), [Obsidian forum](https://forum.obsidian.md/t/maximum-number-of-notes-in-vault/1509/25)).

## Universal MCP means OAuth with three registration paths, a dual-stack transport, and turn-time freshness

The client matrix gives a precise minimum common denominator for one server that every platform can install: a public HTTPS Streamable HTTP endpoint that speaks both 2025-11-25 (sessions, GET stream) and 2026-07-28 (stateless, POST-only, `_meta` versioning, `server/discover`), OAuth 2.1 with RFC 9728 Protected Resource Metadata and RFC 8707 audience binding, CIMD plus DCR plus static-client registration, a header-token mode for quick single-user installs, read-only `search`/`fetch` tools carrying `readOnlyHint`, at most about 20 tools with JSON Schema 2020-12-valid simple schemas, `instructions` tuned for Claude Code's tool search, `Origin` validation, an externalized session store, SSE keepalives and idempotent writes ([mcp_protocol_and_clients.md final tables](mcp-landscape-2026-10-11/notes/mcp_protocol_and_clients.md), [authorization spec](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/basic/authorization/index.mdx), [Streamable HTTP spec](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/basic/transports/streamable-http.mdx)). Against that list we already have the Streamable HTTP transport with sessions, `Origin`/DNS-rebinding protection, 18 annotated tools with `outputSchema`, idempotency on all four write tools, cursor pagination, audit logging and a typed error vocabulary ([our_codebase_inventory.md](mcp-landscape-2026-10-11/notes/our_codebase_inventory.md)). Eighteen tools sits comfortably under Windsurf's hard cap of 100 total tools and Copilot Studio's roughly 128 per agent ([Windsurf docs excerpt](https://docs.windsurf.com/windsurf/cascade/mcp), [StackOne on Copilot Studio](https://www.stackone.com/blog/best-mcp-gateway-for-copilot-studio/)).

What must be built, in order of consequence, starts with **token-to-principal resolution**. The OAuth 2.1 resource server (already planned in Phase 10 and correctly delegated to a managed provider rather than rolled in-house) must map each access token to an `agents` row (tenant, scopes, source weight) so that one URL serves many users and clients, and must validate audience so tokens issued for another server are rejected; the spec is blunt that servers "MUST accept only tokens valid for their own resources and MUST NOT accept or forward any other tokens" ([authorization spec](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/basic/authorization/index.mdx)). The ADR-014 spike should score WorkOS versus Ory Hydra on CIMD support first, since Claude uses a client metadata document only when the authorization server advertises `client_id_metadata_document_supported` and `none` in `token_endpoint_auth_methods_supported` ([Zuplo on Claude connectors](https://zuplo.com/learn/mcp/compatibility/clients/claude-connectors), a secondary source relaying Anthropic docs). Azure DevOps shipped a remote MCP to GA "without support for Claude, ChatGPT, or Cursor" because its identity provider lacked the registration mechanisms those clients need; that is the failure mode to design against ([InfoQ](https://www.infoq.com/news/2026/08/azure-devops-remote-mcp-ga/)). Keep the header-token path: Claude.ai accepts fixed header credentials, Claude Code has `--header`, Zed uses a static `Authorization` header, and Perplexity accepts an API key ([Anthropic help](https://support.claude.com/en/articles/11175166-getting-started-with-custom-connectors-using-remote-mcp), [Zed docs](https://github.com/zed-industries/zed/blob/main/docs/src/ai/mcp.md)). Once OAuth lands, flip `OMNIMIND_REQUIRE_AGENT_KEY` to true so legacy trusted headers stop bypassing scope enforcement (known limitation 8).

Second, **ship ChatGPT's `search`/`fetch` pair** as thin read-only wrappers over `memory_search` and a by-id read, annotated `readOnlyHint: true`. ChatGPT keys its confirmation prompts off that hint ("tools without this hint are treated as write actions and require confirmation"), and while a connector no longer strictly requires the pair, Deep Research and company knowledge still retrieve through it ([devops.com](https://devops.com/chatgpt-developer-mode-full-mcp-access-with-serious-responsibilities/), [Vercel KB](https://vercel.com/kb/guide/mcp-server-chatgpt-connector), both secondary). This is a day of work and unlocks the one client where our naming convention is a liability.

Third, **replace the freshness plan**. Instead of task 10.9's resource notifications, write server `instructions` (Claude Code loads them at session start and truncates at 2,048 characters) that tell hosts to call `status_get` or a new cheap `memory_context(scope)` at the start of relevant turns, set short `ttlMs` with `cacheScope: "private"` on volatile resources once on the new spec, and use `list_changed` sparingly because Claude Code backs off for roughly six hours after five reopens in an hour ([Claude Code MCP docs](https://code.claude.com/docs/en/mcp), [resources spec](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/server/resources.mdx)). The existing `session_start` prompt already encodes this behaviour for clients that render prompts; `instructions` extends it to clients that do not. Phase 12's outbox and webhooks (planned) are the right vehicle for pushing changes to agents and the BoardRoom UI; they are not a substitute for turn-time reads in third-party chat clients.

Fourth, **go dual-stack**. Claude Code's v2 runtime already asks HTTP servers whether they support 2026-07-28 and uses it when they do; everyone else still sends `initialize` with 2025-11-25, and the spec requires that a server claiming 2025-era support keep sessions, the GET stream and resumability ([Claude Code MCP docs](https://code.claude.com/docs/en/mcp), [Streamable HTTP spec](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/basic/transports/streamable-http.mdx)). That means upgrading `@modelcontextprotocol/sdk` from 1.31 to 2.x, adding `server/discover`, `_meta` versioning, mandatory `Mcp-Method`/`Mcp-Name` handling and `CacheableResult` fields, while keeping the current session code. Because SSE resumability is gone in the new revision and "clients must reissue [a lost request] with a new request ID," our existing `idempotencyKey` is the correct defence; extend it to `memory_supersede` and `memory_consolidate` apply calls ([changelog](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/changelog.mdx)). The in-memory session map is safe only while Railway runs one instance; the canonical 2026 failure is `initialize` landing on one isolate and `notifications/initialized` on another, returning 404, which clients mis-report as an SSE 405 ([executor #2187](https://github.com/UsefulSoftwareCo/executor/issues/2187), [python-sdk #520](https://github.com/modelcontextprotocol/python-sdk/issues/520)). Externalize sessions to Postgres before a second instance, not after.

Fifth, **harden against memory poisoning**, which is the active threat class for a shared store. Mark `memory_supersede` and `memory_consolidate` with `_meta["anthropic/requiresUserInteraction"]: true` so Claude Code always prompts (Claude.ai, Cowork, Zed and Copilot Studio do not surface elicitation, so server-side `confirm` arguments remain the fallback), wrap every memory returned to a model with its provenance (source agent, source weight, timestamps), and recommend read-only scopes for Claude.ai connectors because Research mode "can invoke connector tools without further approval" ([Claude Code MCP docs](https://code.claude.com/docs/en/mcp), [Anthropic help](https://support.claude.com/en/articles/11175166-getting-started-with-custom-connectors-using-remote-mcp), [Relativity note on Claude.ai elicitation](https://help.relativity.com/RelativityOne/Content/Relativity/MCP/Anthropic_Claude.htm)). Zep's own guidance after Graphiti's CVE is one key per agent and per-user isolation; we already have both and should say so in docs ([Zep poisoning guide](https://blog.getzep.com/defending-agent-memory-poisoning/)). A schema audit is cheap insurance: Claude Code excludes any tool whose schema fails the 2020-12 meta-schema, flattens root-level `anyOf`/`oneOf`, and requires property names of 1–64 characters in `[A-Za-z0-9_.-]` ([Claude Code MCP docs](https://code.claude.com/docs/en/mcp)).

Finally, **finish the install surface**. We ship four client configs (Claude Desktop, Claude Code, Cursor stdio, ChatGPT HTTP) and Tier-6 smoke tests use curl and the SDK, not a real ChatGPT client ([our_codebase_inventory.md](mcp-landscape-2026-10-11/notes/our_codebase_inventory.md)). Add Claude.ai custom-connector instructions (connections originate from Anthropic's cloud, so a private host needs their IP ranges allowlisted), `gemini mcp add` with `httpUrl`, a Cursor deeplink (`cursor://anysphere.cursor-deeplink/mcp/install?name=…&config=…`), Windsurf `serverUrl`, VS Code `mcp.json`, Zed `context_servers`, and note that Gemini Enterprise and Copilot Studio reject SSE outright, so never add the legacy transport ([Gemini CLI docs](https://github.com/google-gemini/gemini-cli/blob/main/docs/tools/mcp-server.md), [Cursor install links](https://cursor.com/docs/mcp/install-links), [Google Cloud release notes](https://docs.cloud.google.cn/feeds/gemini-enterprise-release-notes.xml), [Microsoft Learn](https://learn.microsoft.com/microsoft-copilot-studio/mcp-add-existing-server-to-agent)). Several of these client facts come from snippets of official pages that were blocked in the research session and warrant a one-click check. Publishing to the official registry under a DNS-verified `com.<domain>/memory` namespace is cheap but the registry is still in preview, verifies namespace control not URL control, and no end-user client is documented as consuming it; the already-planned Connector Directory submission (task 10.11) should be sequenced after OAuth works end-to-end from Claude Desktop ([registry README](https://github.com/modelcontextprotocol/registry), [registry quickstart](https://github.com/modelcontextprotocol/registry/blob/main/docs/modelcontextprotocol-io/quickstart.mdx)).

One open risk the notes could not quantify: `memory_write` runs Haiku fact extraction inside the tool call. Mem0's OpenMemory drew a public bug for `add_memories` blocking more than two minutes, Claude Code moves calls over two minutes to the background, and one multi-agent setup blew a 60-second client timeout ([mem0 #4479](https://github.com/mem0ai/mem0/issues/4479), [Claude Code MCP docs](https://code.claude.com/docs/en/mcp), [Vixl #167](https://github.com/jxburros/Vixl/issues/167)). Measure p95 write latency across clients before public launch; if it exceeds about 20 seconds, return the memory id immediately and extract in the embedding-retry job.

## The graph's next leap is search-driven spotlight and local-first, not a renderer swap

What is already shipped is more than most memory products offer: hover fades everything outside the 1-hop neighbourhood to roughly 12 percent, node radius scales with the square root of degree, local-graph depth runs 0–3 with per-ring fade, search focuses and zooms, filters persist in `sessionStorage`, the inspector shows backlinks and hosts three link editors, the unlinked-mentions panel links in one click, shapes and token colours survive theme changes, `prefers-reduced-motion` is honoured and `?focus=` makes a node shareable ([our_codebase_inventory.md](mcp-landscape-2026-10-11/notes/our_codebase_inventory.md), `KnowledgeGraphView.tsx`, `GraphPage.tsx`, `NodeInspector.tsx`). The Phase 6 research already names per-entity backlinks on entity pages as the next step and rules out a graph database, a cross-encoder and exposing the whole graph as one resource ([IMPROVEMENT-RESEARCH-2026-10-02.md](docs/research/IMPROVEMENT-RESEARCH-2026-10-02.md)); those stay as stated.

The published critiques of force graphs converge on one lesson: hairballs are a density and interpretation problem, visible "clusters" may be layout artefacts, and the remedies with evidence are to show less, add drawn structure and pair the picture with lists ([skewed.de](https://skewed.de/lab/posts/hairball/), [Cambridge Intelligence](https://cambridge-intelligence.com/how-to-fix-hairballs/), [GI 2025](https://www.cs.usask.ca/faculty/dmondal/Presentations/GI25-2.pdf)). Obsidian's own users ask for "a functional local graph for the big graph" because the global view is not actionable ([Obsidian forum](https://forum.obsidian.md/t/design-talk-about-the-graph-view/22594?page=2)). So the first change is a default, not a feature: open the graph page in local mode around the active goal, project or decision with the depth slider at 2 and the inspector listing neighbours grouped by edge type, and make the global map an opt-in overview. The "Focus local" button exists; promote its behaviour to the default (effort S).

The second change is the one that makes the graph "far more searchable": wire the ⌘K palette to `POST /memories/search` and spotlight the hits. Obsidian's built-in graph search "is a filter that hides all non-matching nodes, which loses the surrounding structure"; the community fix draws a glow ring around matches and dims the rest, and Sigma's own tutorial calls hover-dim "the most common interactive pattern in graph visualization" ([Obsidian forum](https://forum.obsidian.md/t/enhanced-graph-search/113084), [Graph Type to Search](https://www.obsidianstats.com/plugins/graph-type-to-search), [Sigma how-to](https://v4.sigmajs.org/how-to/interactivity/hover-search/)). Because hybrid search already returns scores, the client can scale ring intensity by score, `zoomToFit(hits)`, and offer a "Filter" toggle that hides instead. The same palette query should hit an entity search endpoint for tasks and commitments so the palette stops being limited to preloaded store slices. The one engineering risk is hits that are not in the loaded 200-memory subgraph; lazy-fetch them with their 1-hop backlinks via the existing `GET /graph/backlinks/:nodeId` (effort S–M). An `asOf` date picker beside the search box, which the server already supports, gives the graph time travel no competitor's UI offers (effort S).

Third, add a **timeline**. Every entity has `createdAt` and memories carry `validAt`/`invalidAt`; a scrubber that grows the graph chronologically reproduces Obsidian's Animate time-lapse, which users like and want speed controls for, and a Litmaps-style time-axis layout (x = time, y = type lane) fits a product that is about decisions over time ([Obsidian help](https://obsidian.md/help/plugins/graph), [Sourcely on Litmaps](https://www.sourcely.net/resources/research-rabbit-vs-connected-papers-tool-finds-related-studies)). Freeze positions and fade nodes in on scrub to avoid layout thrash (scrubber S, axis layout M).

Fourth, **server-side facets and an edge-type filter**. The graph query schema supports only `types`, `domain`, `memoryLimit` and `includeArchived`; adding `edgeTypes`, `status`, `tags` and a date range as query params keeps the client under its render ceiling and animates diffs instead of refetching everything ([graph.schema.ts](packages/shared/src/validation/graph.schema.ts)). This is a contract change (`docs/contracts/omnimind-api.contract.md`) and pairs naturally with Phase 4's planned recursive-CTE `findRelatedEntities(entityId, hops ≤ 2)`, which would also replace the MCP's N-round-trip BFS in `graph_neighborhood` (facets M; Phase 4 already planned).

Fifth, **communities drawn, not inferred**. Run `graphology-communities-louvain` in a Web Worker, persist community ids (Louvain is non-deterministic across runs), outline each with `bubblesets` and give it one auto label, which reproduces the named-cluster feel reviewers praise in InfraNodus and Kumu ([graphology-communities-louvain](https://unpkg.com/graphology-communities-louvain@2.0.2/README.md), [bubblesets](https://npmjs.org/package/bubblesets), [InfraNodus](https://infranodus.com/use-case/text-network-analysis), [Kumu](https://kumu.io/markets/network-mapping)). Pair it with semantic-zoom labels: rank nodes by centrality times recency and show a label only when its box does not collide with a higher-ranked label at the current zoom, with hysteresis to stop flicker ([rtopmap](https://arxiv.org/pdf/1706.04979)). Both fit in the existing `nodeCanvasObject` (M and S–M).

Sixth, the **accessibility and colour baseline**: keep shapes as the redundant channel, move to Okabe-Ito without black or Tol "muted" for the seven-to-eight node types with lightness-derived dark-mode variants, keep label halos, and add Tab/arrow traversal from the selected node plus an off-canvas node table, which is the accepted baseline for graphs ([Okabe-Ito reference](https://dev.conceptviz.app/fr/blog/okabe-ito-palette-hex-codes-complete-reference), [Tol schemes](https://www.stats.bris.ac.uk/R/web/packages/khroma/vignettes/tol.html), [Oracle ACR](https://www.oracle.com/anz/corporate/accessibility/templates/t2-19397.html)). Add a back/forward focus history because Obsidian users explicitly complain that graph search history is lost (S–M overall).

The renderer question should be answered by a benchmark, not a rewrite. `react-force-graph-2d` is adequate into the low thousands of visible nodes if painting is cheap; Sigma.js plus Graphology (WebGL, MIT, "tens of thousands of nodes") is the lowest-risk step up because the same ecosystem supplies ForceAtlas2 in a worker, noverlap and Louvain, with `react-sigma` as the React binding; Cosmograph does the simulation on the GPU but its packaged React library is CC-BY-NC-4.0, which a paid SaaS cannot use without a quote-only commercial licence ([react-force-graph](https://github.com/vasturiano/react-force-graph), [Sigma v4 rendering](https://v4.sigmajs.org/concepts/rendering/), [react-sigma](https://github.com/sim51/react-sigma), [Cosmograph licensing](https://cosmograph.app/licensing/)). No library publishes reproducible 2026 FPS numbers at 1k/10k/50k nodes, so measure the real tenant graph behind the current `KnowledgeGraphViewHandle` interface and swap only if visible nodes exceed roughly 2–3k. A server-side UMAP "semantic map" of memory embeddings is a genuine differentiator (we already store 1536-dim vectors) but depends on an OmniMind endpoint caching 2D projections per tenant, since the client must not compute over raw embeddings ([UMAP as layout](https://arxiv.org/pdf/2107.01887)). The "explain this neighbourhood" summary via Haiku and a natural-language-to-Zod-filter "ask the graph" are worth doing after the above; the Text2Cypher literature shows base models mis-generate complex queries, so constrain generation to a filter schema and show the generated chips ([arXiv 2412.10064](https://arxiv.org/html/2412.10064v1)).

## Conclusion

The research reframes the question. "Is there a better tool" has a clean answer (no single one), but the reason is instructive: the market has solved distribution and left data model, governance and intelligence unsolved, while OmniMind did the reverse. The 265 registry entrants and Zep's August 2026 Memory MCP prove that an OAuth-secured remote server with save and recall tools is now a weekend project; the things nobody has built, idempotent writes, decision and commitment lifecycles, persisted contradiction alerts, agent-scoped keys with audit, are the things that take a year of product judgment. That asymmetry is the strategy: spend the next six weeks closing the commoditized front-door gap precisely because it is commoditized, then let the unique layer carry the positioning.

The second shift is in what "stay up to date" can mean. The protocol's own 2026 rewrite made the server-to-client back-channel weaker, not stronger, and no chat client turns a notification into a turn. A universal memory therefore wins on how reliably every client reads it at the right moment, which is a prompt-engineering and tool-design problem (`instructions`, a cheap context tool, short cache hints) rather than a transport problem. The same logic applies to the graph: the data already holds time, validity and scores that no competitor exposes, and the gains come from putting them on the canvas, not from a faster canvas. The honest caveats stand: several client and pricing facts rest on search excerpts of pages the research sandbox could not open, our retrieval margin is thin, and `memory_write` latency across real clients is unmeasured. Those are the three things to verify in the first week.
