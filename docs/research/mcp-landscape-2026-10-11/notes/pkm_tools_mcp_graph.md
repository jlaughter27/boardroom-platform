# PKM / note tools with Obsidian-style graph views + MCP access, as shared AI memory (state as of 2026-10-11)

Scope note: this covers Obsidian, Notion, Logseq, Anytype, Tana, Reflect, Capacities, Heptabase, Khoj, AFFiNE, plus Basic Memory and Amplenote (which shipped official MCP "second brain" offerings) and brief notes on Quartz / Foam / Dendron. Research constraint: the session's egress proxy blocked direct fetches of developers.notion.com, affine.pro, reflect.app, help.obsidian.md, docs.capacities.io, discuss.logseq.com, forum.obsidian.md and Substack (HTTP 403 policy denial), and Reddit is unavailable to the search tool. Primary GitHub pages and the Obsidian help / Logseq docs GitHub mirrors were fetched directly; everything else is from search-engine extracts of the cited pages. Where a claim rests on a vendor blog or a competitor's blog, it is flagged.

## KQ1 — For each tool: is there an official or well-maintained MCP server, does it write, is it local-only or remote/OAuth, and which AI clients are documented?

### Takeaway
As of October 2026 almost every PKM tool is reachable by MCP, but in two very different shapes: (a) local-only servers that die when the desktop app closes (Obsidian Local REST API, Logseq, Anytype, Tana Outliner local) and (b) hosted/OAuth remote servers (Notion, Tana remote, Heptabase private beta, AFFiNE Cloud, Reflect, Basic Memory Cloud). Only Notion, Tana, Anytype, Logseq, AFFiNE, Heptabase, Reflect, Capacities (API) and Basic Memory have a first-party server; Obsidian still has none and relies on a 3k-star community plugin.

### Cited Findings

**Obsidian**

- A forum feature request for an "Official MCP core plugin" says of the community servers: "it is very very difficult to identify which one is useful, will be maintained for the future" — [Obsidian Forum feature request](https://forum.obsidian.md/t/official-mcp-core-plugin/109276)
- The de-facto standard is the community **Local REST API** plugin (coddingtonbear), 3.0k GitHub stars / 354 forks, which now has a **built-in MCP server** at `https://127.0.0.1:27124/mcp/` (or `http://127.0.0.1:27123/mcp/`), Streamable HTTP, bearer API key in `Authorization`; it serves a stateless `2026-07-28` protocol revision and sessionful revisions `2024-10-07` through `2025-11-25`. Documented clients: Claude Code (native HTTP), Claude Desktop (via `mcp-remote` bridge), Cursor. Obsidian must be running. — [github.com/coddingtonbear/obsidian-local-rest-api](https://github.com/coddingtonbear/obsidian-local-rest-api)
- Same plugin's REST surface: GET/PUT/POST/PATCH/DELETE on `/vault/{path}` including binaries; PATCH targets headings, block references and frontmatter keys; `POST /search/simple/` (Obsidian fuzzy FTS) and `POST /search/` with JsonLogic; `/commands/` list+execute; `/open/{path}`; tags; `/active/`; SSE event streams; PATCH supports optimistic concurrency via `ifMatch` version — [github.com/coddingtonbear/obsidian-local-rest-api](https://github.com/coddingtonbear/obsidian-local-rest-api)
- The plugin's community listing describes the built-in MCP endpoint at `/mcp/` with Streamable HTTP and API-key auth, requiring Obsidian running — [community.obsidian.md/plugins/obsidian-local-rest-api](https://community.obsidian.md/plugins/obsidian-local-rest-api)
- Older guides (May 2026) still describe the two-piece setup: Local REST API plugin + separate stdio bridge `mcp-obsidian` translating MCP calls to HTTP — [mcp.directory guide 2026](https://mcp.directory/blog/obsidian-mcp-complete-guide-2026); the Docker MCP catalog ships `mcp/obsidian` — [hub.docker.com/r/mcp/obsidian](https://hub.docker.com/r/mcp/obsidian)

**Anytype**
- Official `anyproto/anytype-mcp` (npm `@anyproto/anytype-mcp`), 532 stars, 272 commits, 17 open issues; generated from Anytype's OpenAPI spec (v2, falls back to v1). Auth: API key as Bearer in `OPENAPI_MCP_HEADERS` plus `Anytype-Version: 2025-11-08` header; keys created in app Settings → API Keys or `npx -y @anyproto/anytype-mcp get-key`. Transport: launched as local command (stdio). Default API base `http://127.0.0.1:31009` (local desktop API). Limitations: no automatic retries ("Failed writes must be retried manually with the same request key"), a global `Idempotency-Key` header is rejected, no persistent spec cache (restart after Anytype updates) — [github.com/anyproto/anytype-mcp](https://github.com/anyproto/anytype-mcp)

### Inferences
- Only three tools give a founder a *first-party, remote, OAuth-authenticated, writable* MCP today: Notion (full CRUD), Tana remote (writes become proposals), and Heptabase (private beta, write-only inbox/journal). AFFiNE is remote but writes are still "rolling out"; Reflect is remote but documented as read/search.
- Obsidian is the richest ecosystem but structurally the weakest "shared memory" substrate: no official server, two incompatible access paths (app REST vs raw filesystem), and remote access only via community hosts.
- Logseq's official MCP is the most "transactional" local option (batch, dry-run, undo/redo, UI validations) but is still missing property read/write on arbitrary nodes and child-block access, which matters for structured memory.
- Anytype's official server explicitly forbids a global Idempotency-Key and offers no retries, so multi-agent idempotency has to be built by the caller.

## KQ2 — Graph view features: filters, groups/colors, local depth, search-to-highlight, time-lapse, clustering, 10k+ performance, 3D, mobile

### Takeaway
Obsidian's built-in graph remains the reference (filters, color groups, local depth slider, forces, time-lapse, mobile) but degrades badly past ~10–25k notes; Anytype and Logseq have serviceable but less configurable graphs; Capacities is local-only (no global graph); Notion, Tana, AFFiNE, Khoj and Heptabase have no native force-graph (Notion only via third-party add-ons; Heptabase uses whiteboards).

## KQ4 — What breaks with several AI agents writing concurrently (conflicts, sync, idempotency, provenance)? Are there structured entity types or just pages?

### Takeaway
None of the PKM tools offers agent-level provenance or idempotent write semantics out of the box; markdown-file tools (Obsidian, Logseq OG, Basic Memory) have no concurrency story beyond optional per-process mutexes, sync tools create conflict copies, and only Logseq DB, Tana, Anytype and Notion have first-class typed entities (tasks with status, supertags, object types, databases).

### Cited Findings
- Markdown "has no real concurrent-access story, so simultaneous writers can corrupt data"; recommends SQLite in WAL mode instead — [Substack, "Stop Calling It Memory"](https://limitededitionjonathan.substack.com/p/stop-calling-it-memory-the-problem) (search extract; full post unreachable)
- Obsidian "MCP Connector" plugin claims it routes writes through Obsidian's vault API "with a process-wide mutex" to prevent lost updates when two MCP writes hit the same file (developer claim) — [community listing](https://community.obsidian.md/plugins/mcp-tools-istefox)
- Local REST API: only optimistic concurrency on PATCH (`ifMatch` version); no file locking documented — [GitHub](https://github.com/coddingtonbear/obsidian-local-rest-api)
- Direct-FS servers (e.g., obsidian-memory-layer-mcp) use plain file I/O with no locking described — [GitHub](https://github.com/honam867/obsidian-memory-layer-mcp)
- A guide keeps the MCP read-only, moves writes to hooks, and uses a single writer for the SQLite index to avoid `SQLITE_BUSY` — [blakecrosley.com guide (2026)](https://blakecrosley.com/guides/obsidian)
- Team + Obsidian Sync + Claude MCP: two sync services on one folder produce repeated conflicts; fix was one-way sync to a read-only copy with Claude writing to a separate inbox folder, or a private git remote — [Obsidian Forum](https://forum.obsidian.md/t/using-claude-mcp-in-a-team-with-sync/100993)

- Multi-agent idempotency has to be implemented client-side everywhere (Anytype even rejects a global idempotency header); Notion's and Logseq's servers at least validate writes server-side, whereas raw-file paths silently accept clobbering.

### Gaps
- No documented incident reports or benchmarks of concurrent multi-agent writes for any tool; all evidence is anecdotal or architectural.
- Notion's hosted MCP concurrency/last-write-wins semantics for simultaneous page updates are undocumented in reachable sources.
- Tana's local MCP write safety (no proposals locally?) could not be confirmed.

### Inferences
- A founder *can* get "one memory, many AI clients" with Notion today (every major client speaks remote OAuth MCP), but loses graph UX, headless agents, idempotency and provenance, and gets rate-limited; with Obsidian they get graph UX and portability but must self-host a server, an index, a change feed and a write-serialization layer — i.e., rebuild most of a custom memory service around a file folder.
- The defensible scope for a custom system (per this repo's existing OmniMind design: typed entities, validation pipeline, `Idempotency-Key`, supersede/provenance, hybrid retrieval, backlinks, graph BFS) is precisely the set of gaps shared by all PKM tools; the PKM graph view is a UX feature a custom system can match with a scoped local graph (depth slider, type filters, search highlight) without needing 10k-node global-graph performance.
- The cheapest hybrid is "custom system of record + Markdown Mirror into an Obsidian vault" (mirroring Logseq's own read-only Markdown Mirror pattern and Basic Memory's Obsidian compatibility), giving users the Obsidian graph for exploration while agents write only through the validated API.

### Gaps
- Live verification of official docs for Notion, AFFiNE, Reflect and Capacities was blocked; the table rows for those rely on secondary extracts.
- No head-to-head benchmark exists for retrieval quality or write latency across these MCP servers.
