## Key Question 1: Which spec revision is current, and what changed in each revision that matters for a memory server?

### Takeaway
The current MCP specification is **2026-07-28** (released as a full version on 2026-07-28 after a 2026-05-21 release candidate). It is the largest rewrite since launch: the core is now stateless (no `initialize`, no `Mcp-Session-Id`), server-initiated requests are replaced by Multi Round-Trip Requests, `resources/subscribe` and the HTTP GET notification stream are replaced by a `subscriptions/listen` stream, Tasks moved to an extension, and OAuth Dynamic Client Registration is formally deprecated in favor of Client ID Metadata Documents. A memory server shipping in October 2026 must still speak the 2025-era protocol (sessions + GET stream) because most shipping clients have not moved yet (see Q3).

### Cited Findings

**Version lineage**
- The 2026-07-28 revision "became the current version on its target date of 2026-07-28" and was "published as a release candidate on 2026-05-21"; it supersedes 2025-11-25 — [MCP blog: The 2026-07-28 Specification](https://blog.modelcontextprotocol.io/posts/2026-07-28/) **[primary]**; RC post: [The 2026-07-28 MCP Specification Release Candidate](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/) **[primary]**.
- The official blog index (checked 2026-10-11) shows three posts: "The New MCP Roadmap" (2026-08-22), "The 2026-07-28 Specification" (2026-07-28, "a full release, not a release candidate"), and "The Official Ruby SDK for MCP Reaches 1.0" (2026-07-27) — [blog.modelcontextprotocol.io](https://blog.modelcontextprotocol.io/) **[primary]**.
- Prior revisions referenced in the spec repo's changelogs: 2024-11-05, 2025-03-26, 2025-06-18, 2025-11-25, 2026-07-28 — [2026-07-28 changelog (raw)](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/changelog.mdx), [2025-11-25 changelog (raw)](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2025-11-25/changelog.mdx) **[primary]**.

**2025-11-25 changes (per its changelog)** — [2025-11-25 changelog](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2025-11-25/changelog.mdx) **[primary]**
- Tasks: "Experimental support for durable requests with polling and deferred result retrieval (SEP-1686)."
- Elicitation URL mode added (SEP-1036); default values for all primitive types in elicitation schemas (SEP-1034); titled/untitled single- and multi-select enums in `ElicitResult`/`EnumSchema` (SEP-1330).
- Sampling gained tool calling via `tools` and `toolChoice` (SEP-1577).
- OAuth Client ID Metadata Documents (CIMD) added "as a recommended client registration mechanism (SEP-991)"; incremental scope consent via `WWW-Authenticate` (SEP-835); Protected Resource Metadata discovery aligned with RFC 9728 (SEP-985); OpenID Connect Discovery 1.0 for authorization-server discovery (PR #797).
- Tool naming guidance (SEP-986); icons for tools/resources/prompts (SEP-973); JSON Schema 2020-12 as default dialect (SEP-1613); invalid `Origin` headers must get HTTP 403 in Streamable HTTP (PR #1439); "Polling SSE streams with server-initiated disconnects (SEP-1699)"; input validation errors should be Tool Execution Errors (SEP-1303).
- Governance: formal governance (SEP-932), Working/Interest Groups (SEP-1302), SDK tiering (SEP-1730). The changelog does not list a "server identity" SEP; the closest item is an optional `description` on `Implementation`. Enterprise Managed Authorization and an extensions framework are not mentioned in this changelog.

**2026-07-28 changes (per its changelog and blog)** — [2026-07-28 changelog](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/changelog.mdx), [release blog](https://blog.modelcontextprotocol.io/posts/2026-07-28/) **[primary]**
- Sessions removed (SEP-2567): `Mcp-Session-Id` gone from Streamable HTTP; "List endpoints no longer vary per connection. Cross-call state uses server-issued handles passed as tool arguments."
- Stateless protocol (SEP-2575): `initialize`/`initialized` handshake removed; every request carries protocol version, `clientInfo` and client capabilities in `_meta` (`io.modelcontextprotocol/protocolVersion`, `io.modelcontextprotocol/clientInfo`, `io.modelcontextprotocol/clientCapabilities`); version mismatches return `UnsupportedProtocolVersionError`.
- `server/discover` added (SEP-2575): "Servers must implement it to advertise versions, capabilities, and identity"; clients may call it first or use it as a stdio back-compat probe. (The blog calls it optional for clients.)
- `subscriptions/listen` added (SEP-2575): "replaces the HTTP GET endpoint and `resources/subscribe`/`unsubscribe`. It is a long-lived stream where clients opt into notification types."
- Removed: `ping`, `logging/setLevel`, `notifications/roots/list_changed`; SSE resumability (`Last-Event-ID`) removed — "A broken stream loses the in-flight request, and clients must reissue it with a new request ID."
- Tasks moved to extension `io.modelcontextprotocol/tasks` (SEP-2663): blocking `tasks/result` becomes polling via `tasks/get`; `tasks/update` added; `tasks/list` removed; "servers may return task handles without per-request opt-in."
- Multi Round-Trip Requests (SEP-2322): servers return `resultType: "input_required"` with `inputRequests`, "replacing server-initiated `roots/list`, `sampling/createMessage`, and `elicitation/create`. Clients retry the original request with `inputResponses`." All results now carry `resultType` ("complete" or "input_required"); results from older servers lacking it are treated as complete.
- Transport headers (SEP-2243): POST requests require `Mcp-Method` and `Mcp-Name`; `x-mcp-header` maps tool parameters to custom headers.
- Cache hints (SEP-2549): `tools/list`, `prompts/list`, `resources/list`, `resources/read`, `resources/templates/list` results "require `ttlMs` and `cacheScope` via `CacheableResult`"; deterministic list order.
- Authorization: RFC 9207 `iss` validation (SEP-2468); `application_type` required in DCR (SEP-837); credentials keyed by issuer and never reused across authorization servers (SEP-2352); "RFC 7591 DCR is deprecated in favor of Client ID Metadata Documents" (PR #2858).
- Schema: `inputSchema`/`outputSchema` accept any JSON Schema 2020-12 keywords; `structuredContent` accepts any JSON value (SEP-2106). Resource-not-found error moves from `-32002` to `-32602`.
- Elicitation cleanup: `notifications/elicitation/complete` and URL-mode `elicitationId` removed; correlation via `requestState`.
- `extensions` field added to `ClientCapabilities` and `ServerCapabilities`; OpenTelemetry `traceparent`/`tracestate`/`baggage` documented in `_meta` (SEP-414).
- Deprecations (SEP-2577, SEP-2596): Roots, Sampling, Logging deprecated ("keep working for at least twelve months, and new implementations shouldn't adopt them"); legacy HTTP+SSE transport formally deprecated with a year-long offramp; feature lifecycle policy sets a 12-month minimum deprecation window.
- SDKs: "TypeScript, Python, Go, and C# support the new spec. The Rust SDK is in beta." Blog: "Developers who depended on session identifiers face the largest migration cost."
- Extensions named by the blog: Tasks, MCP Apps, Enterprise Managed Authorization (EMA) — [release blog](https://blog.modelcontextprotocol.io/posts/2026-07-28/) **[primary]**.

**2026-07-28 Streamable HTTP details** — [streamable-http.mdx (raw)](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/basic/transports/streamable-http.mdx) **[primary]**
- Single endpoint, **POST only**; servers supporting only this revision return 405 to GET/DELETE. `MCP-Protocol-Version` header on every POST must match the `_meta` version (mismatch = 400, `HeaderMismatch` -32020). `Mcp-Method` on all requests; `Mcp-Name` on `tools/call`, `resources/read`, `prompts/get`.
- Responses are a single JSON object or a request-scoped SSE stream; `subscriptions/listen` "is a POST whose SSE response stays open and carries only the change notifications the client opted into."
- Servers MUST validate `Origin` (403 on invalid) against DNS rebinding; SHOULD send SSE comment keepalives on listen streams and `X-Accel-Buffering: no`; "The spec gives no specific timeout values."
- Backward compatibility: "Servers that also support revisions 2025-03-26 through 2025-11-25 must implement that revision's sessions, GET stream, and resumability." Clients detect legacy servers when a modern request returns 400/404/405 with an unrecognized body, then fall back to `initialize`.

**Tool annotations, structured output, consent (2026-07-28 tools page)** — [tools.mdx (raw)](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/server/tools.mdx) **[primary]**
- "Clients MUST treat annotations as untrusted unless they come from trusted servers."
- `outputSchema`/`structuredContent`: servers MUST return conforming results; clients SHOULD validate; servers SHOULD also include serialized JSON in a text block for back-compat.
- Tool names SHOULD be 1–128 chars, `[A-Za-z0-9_.-]`, unique per server; aggregating clients SHOULD prefix a server identifier.
- "A human SHOULD always be in the loop with the ability to deny tool invocations"; clients SHOULD show confirmation prompts for sensitive operations.
- `tools/list` MUST NOT vary per connection but MAY vary by authorization presented.

### Inferences
- For a memory server in October 2026 the practical target is **dual-stack**: implement 2026-07-28 (stateless, POST-only, `_meta` versioning, `subscriptions/listen`, `ttlMs`/`cacheScope`) *and* 2025-06-18/2025-11-25 (sessions, GET stream, `resources/subscribe`). The spec explicitly requires the legacy machinery if you claim 2025-era support, and Q3 shows most clients still negotiate 2025-era.
- Because `tools/list` may vary by authorization but not by connection, per-tenant tool sets (e.g., hiding write tools for read-only tokens) are spec-legal in both generations.
- The removal of SSE resumability means a memory server should make every write idempotent (e.g., `Idempotency-Key`-style arguments), since clients must re-issue interrupted requests with a new request ID.

- Could not open the official site pages (modelcontextprotocol.io was unreachable through the proxy); all spec text came from the GitHub raw files on `main`, which track 2026-07-28 and may include post-release editorial edits.

## Key Question 2: Resource subscriptions and `notifications/resources/updated` — can a server push "memory changed," or must clients poll / re-read?

### Takeaway
The protocol has a push primitive (2025-era `resources/subscribe` → `notifications/resources/updated`; 2026-07-28 `subscriptions/listen` with `resourceSubscriptions`), but it is a *lightweight "re-read this URI" signal with no durability or replay*, and the only shipping client evidence I found of honoring update streams is Claude Code holding open a `list_changed` stream on 2026-07-28 connections. No evidence was found that any major chat client (Claude.ai, ChatGPT, Gemini, Copilot, Perplexity) subscribes to resources or wakes the model on a notification. Practically, freshness must come from **tool calls at turn time** (plus `ttlMs`/`cacheScope` hints and `list_changed` to refresh tool lists).

### Cited Findings
- 2026-07-28 resources page: `resources` capability has independent flags `listChanged` and `subscribe`; "`subscribe` means the server supports update notifications for resources requested through `subscriptions/listen` with the `resourceSubscriptions` filter"; "The server delivers `notifications/resources/updated` on the resulting stream whenever a watched resource changes"; after an update "the client calls `resources/read` to get the new contents." This page "does not define a `resources/subscribe` method" — [resources.mdx (raw)](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/server/resources.mdx) **[primary]**.
- 2026-07-28 subscriptions pattern: `subscriptions/listen` params `notifications: {toolsListChanged, promptsListChanged, resourcesListChanged, resourceSubscriptions[]}`; server MUST first send `notifications/subscriptions/acknowledged` listing the honored subset; subscriptionId is the JSON-RPC request id carried in `_meta` `io.modelcontextprotocol/subscriptionId`; stream ends on client cancel (HTTP: close SSE), server teardown, or transport close; "The document does not address ... whether notifications sent while a client is disconnected are buffered or replayed, whether there are event IDs or a resume mechanism, any delivery guarantees." On stdio the client MUST re-send `subscriptions/listen` after reconnect; "The server keeps no subscription state across reconnections." — [subscriptions.mdx (raw)](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/basic/patterns/subscriptions.mdx) **[primary]**.
- 2025-06-18 schema defines `resources/subscribe`, `resources/unsubscribe`, `notifications/resources/updated`; the 2026-07-28 revision uses `subscriptions/listen` instead — [2026-07-28 changelog](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/changelog.mdx) **[primary]**; corroborated by search summary of community issues (secondary) — [search result set](https://github.com/chattocorp/chatto/issues/2248).
- Claude Code (v2 runtime, 2026-07-28 connections): "Receives `list_changed` notifications from servers on the newer protocol revision over a stream it holds open"; if the stream closes within 10 s it reopens up to 3 times; after five reopens in an hour it waits ~6 hours. All runtimes: "Interactive sessions refetch tools, prompts, and resources on `list_changed`. `-p` and Agent SDK sessions refresh only the tool list." The page does not mention `notifications/resources/updated` handling — [Claude Code MCP docs](https://code.claude.com/docs/en/mcp) **[primary]**.
- Claude Code offers a WebSocket transport (`type: "ws"`) "for remote MCP servers that push events to Claude unprompted" (header auth only, no OAuth, 5-minute idle timeout), and a `claude/channel` capability for servers that push messages into a session — but "The v2 runtime does not register channel servers on protocol revision 2026-07-28" because "that revision can't carry channel messages" — [Claude Code MCP docs](https://code.claude.com/docs/en/mcp) **[primary]**.
- Zed "handles `notifications/tools/list_changed`, so it reloads a server's tool list when the server changes tools at runtime" — [Zed docs (GitHub)](https://github.com/zed-industries/zed/blob/main/docs/src/ai/mcp.md) **[primary]**.
- A 2025-10-16 third-party test report found "NO major MCP client automatically reads resources"; Claude Desktop and VS Code only via manual attachment — [DollhouseMCP research report](https://glama.ai/mcp/servers/@DollhouseMCP/DollhouseMCP/blob/62c9b46e851b3753b28f2b916e6379c465abb9d3/docs/development/MCP_RESOURCES_SUPPORT_RESEARCH_2025-10-16.md) **[secondary, dated 2025-10]**.
- Community issue (Chatto #2248) notes the subscription signal "doesn't guarantee durable delivery, wake a model, or start an agent turn" — [chatto issue](https://github.com/chattocorp/chatto/issues/2248) **[secondary]**.
- A Go SDK issue reports the subscription table "is keyed by URI and session only, so credentials sharing a session can receive each other's notifications" — [go-sdk #1265](https://github.com/modelcontextprotocol/go-sdk/issues/1265) **[secondary; SDK bug tracker]**.
- 2026-07-28 cache hints: `resources/read` and list results carry `ttlMs` and `cacheScope` (example: `ttlMs: 60000`, `cacheScope: "private"`) — [resources.mdx](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/server/resources.mdx) **[primary]**.
- Claude Code tool-search guidance for server authors: server `instructions` are loaded at session start and used to decide when to search for tools; tool descriptions and instructions are truncated at 2,048 chars — [Claude Code MCP docs](https://code.claude.com/docs/en/mcp) **[primary]**.

### Inferences
- There is no client-side mechanism today that turns a server notification into an *assistant turn*. A "memory changed" push can at best (a) refresh cached tool/resource lists in Claude Code/Zed/VS Code-class clients, or (b) be observed by a bespoke client. For chat products the assistant only sees memory when it calls a tool (or reads a resource the user attached).
- Design consequence: the memory server should expose a cheap, always-called "context/status" tool (e.g., `memory_context(scope)`) and put strong guidance in server `instructions` so hosts call it at the start of relevant turns; set short `ttlMs` on volatile resources and `cacheScope: "private"` for per-user data. `list_changed` should be used sparingly (Claude Code backs off aggressively on flapping streams).
- Multi-tenant correctness: key subscription state by (principal, URI), not (session, URI), given the Go SDK bug pattern.

### Gaps
- No vendor documentation found stating whether Claude Desktop/Claude.ai, VS Code Copilot, Cursor, ChatGPT or Gemini honor `resources/subscribe` or `subscriptions/listen` for resource updates (the official clients feature matrix at modelcontextprotocol.io/clients was unreachable and its repo path could not be located; `docs/clients.mdx` returned 404).

## Key Question 3: Client support matrix for remote MCP servers (transport, OAuth, write tools, resources/prompts/elicitation, enterprise allow-listing)

### Takeaway
Every major client now accepts remote Streamable HTTP servers; SSE is deprecated everywhere and already removed in Copilot Studio and Gemini Enterprise. OAuth is optional in most consumer clients (no-auth or header/API-key servers are accepted) but effectively required for shared/team use; the registration mechanisms clients can perform differ (CIMD preferred by Claude; DCR still the default for Cursor/Gemini CLI/Raycast "Dynamic"; static client credentials supported by Claude Code, Raycast, Copilot Studio, Claude.ai admins). Write tools are allowed everywhere with per-call confirmation (ChatGPT keys confirmation off `readOnlyHint`; Claude Code honors `_meta["anthropic/requiresUserInteraction"]`). Resources/prompts/elicitation are supported by developer clients (Claude Code, Cursor, Gemini CLI, VS Code), partially by Zed (prompts, no elicitation), and are tools-only in the Claude API connector, Copilot Studio, and (per third-party reports) Claude.ai/Cowork for elicitation. Protocol-revision adoption of 2026-07-28 is confirmed only for Claude Code (v2 runtime) and AWS Bedrock AgentCore Gateway; all other clients should be assumed 2025-era.

## Key Question 4: The official MCP Registry — publishing, namespace verification, consumers

### Takeaway
registry.modelcontextprotocol.io launched in preview on 2025-09-08 with an API freeze (v0.1) on 2025-10-24; I found no official announcement of GA as of 2026-10-11. Publishing is via the `mcp-publisher` CLI and a `server.json`; remote-only servers publish a `remotes` array (`streamable-http` + URL) with no package. Namespaces are verified by GitHub OAuth/OIDC (`io.github.<user>/...`) or DNS/HTTP challenge for reverse-DNS names. The registry hosts metadata only and verifies namespace control, not control of the remote URL. Which end-user clients consume the public registry is not documented; GitHub Copilot consumes *internal* registries configured by admins.

### Cited Findings
- "The registry launched in preview on 2025-09-08"; "On 2025-10-24, the Registry API entered an 'API freeze (v0.1)'"; "a general availability (GA) release will follow later"; four namespace methods: "GitHub OAuth (login), GitHub OIDC (from GitHub Actions), DNS verification, and HTTP verification"; examples `io.github.domdomegg/...` and `me.adamjones/...` — [modelcontextprotocol/registry README](https://github.com/modelcontextprotocol/registry) **[primary]**.
- Publishing steps: install `mcp-publisher`; `mcp-publisher init` generates `server.json`; `name` must match package ownership marker (`mcpName` in `package.json` for npm); `description` ≤100 chars; `packages[]` with `registryType`, `identifier`, `version`, `transport`; `remotes[]` with `type` (example `streamable-http`) and `url`; `mcp-publisher login github` (device code) then `mcp-publisher publish`; verify at `/v0.1/servers?search=<name>`. "If a server is available only at a public remote endpoint, you can publish metadata without a package... The Registry verifies control of the namespace, not control of the remote URL." "the MCP Registry only hosts metadata, not artifacts." — [Registry quickstart](https://github.com/modelcontextprotocol/registry/blob/main/docs/modelcontextprotocol-io/quickstart.mdx) **[primary]**.
- The quickstart "does not say which clients consume the registry"; README names none — same sources **[primary]**.
- GitHub Copilot: admins point orgs/enterprises at an *internal* MCP registry URL; "Allow all" surfaces registry servers as recommendations, "Registry-only" makes the catalog a hard boundary (public preview, VS Code Stable, 2025-11-18) — [GitHub changelog](https://github.blog/changelog/2025-11-18-internal-mcp-registry-and-allowlist-controls-for-vs-code-stable-in-public-preview/) **[primary; snippet]**.

## Key Question 5: Security guidance a shared read/write memory server must follow

### Takeaway
The 2026-07-28 authorization spec is normative and strict: RFC 9728 Protected Resource Metadata is mandatory; tokens must be audience-bound (RFC 8707 `resource`) and never passed through; PKCE S256 is mandatory; CIMD redirect URIs must be exact-matched and the hostname displayed; proxies with static client IDs must obtain per-client consent (confused deputy). Tool annotations are untrusted by clients, humans should stay in the loop, and tool results/descriptions are the primary prompt-injection and tool-poisoning vector — vendors (Anthropic, OpenAI) explicitly warn users that custom connectors are unverified.

### Cited Findings
- Authorization baseline (2026-07-28): "MCP servers MUST implement RFC 9728 Protected Resource Metadata. Clients MUST use it for authorization server discovery"; auth servers "MUST provide RFC 8414 or OpenID Connect Discovery"; clients "MUST send the RFC 8707 `resource` parameter in both authorization and token requests"; servers "MUST validate tokens and confirm they were issued specifically for them as the audience"; "Clients MUST NOT send tokens to a server unless the server's own authorization server issued them. Servers MUST accept only tokens valid for their own resources and MUST NOT accept or forward any other tokens"; bearer tokens in header only, never query string; invalid/expired tokens → 401; insufficient scope → 403 `insufficient_scope` with required `scope` + `resource_metadata`; "Servers SHOULD NOT include `offline_access` in `WWW-Authenticate` scopes or `scopes_supported`" — [authorization/index.mdx (raw)](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/basic/authorization/index.mdx) **[primary]**.
- Security considerations (2026-07-28): clients "MUST implement PKCE... MUST use the S256 code challenge method"; if `code_challenge_methods_supported` is missing, clients "MUST refuse to proceed"; "MCP servers MUST only accept tokens specifically intended for themselves"; a server acting as client to upstream APIs "MUST NOT pass through the token it received from the MCP client"; proxy servers using static client IDs "MUST obtain user consent for each" dynamically registered client; auth servers "MUST validate exact redirect URIs against pre-registered values" and for CIMD "MUST clearly display the redirect URI hostname during authorization" and "SHOULD display additional warnings for `localhost`-only redirect URIs"; CIMD fetchers "SHOULD consider" SSRF; "SHOULD issue short-lived access tokens" — [security-considerations.mdx (raw)](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/basic/authorization/security-considerations.mdx) **[primary]**.
- Client registration precedence: pre-registered → CIMD (if `client_id_metadata_document_supported`) → DCR (if `registration_endpoint`) → prompt user; CIMD doc requires `client_id` (== its URL), `client_name`, `redirect_uris`; DCR deprecated (MAY) and clients must set `application_type` (`native` for CLI/desktop/localhost, `web` otherwise); credentials keyed by issuer; CIMD IDs are portable — [client-registration.mdx (raw)](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/basic/authorization/client-registration.mdx) **[primary]**.
- Transport: servers "MUST validate the `Origin` header and return 403 for invalid origins" (DNS rebinding); `x-mcp-header`-mirrored parameters "are visible to network intermediaries, so sensitive values... should not use it"; "For stateful tools, servers should check authorization against a handle on every call" — [streamable-http.mdx](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/basic/transports/streamable-http.mdx), [tools.mdx](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/server/tools.mdx) **[primary]**.
- Tools: "Clients MUST treat annotations as untrusted unless they come from trusted servers"; servers "MUST validate all tool inputs, implement access controls, rate limit invocations, and sanitize outputs"; clients "SHOULD validate tool results before passing them to the LLM" — [tools.mdx](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/server/tools.mdx) **[primary]**.
- Session-hijacking guidance from the 2025-06-18 best-practices page could not be retrieved (404 at the guessed path); the 2026-07-28 removal of sessions moots most of it — [changelog](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/changelog.mdx) **[primary]**.
- Vendor warnings: Anthropic — "Custom connectors aren't verified by Anthropic, so users should connect only to trusted servers and watch for prompt injection and unexpected changes in tool behavior"; Research mode can call tools without approval — [Anthropic help](https://support.claude.com/en/articles/11175166-getting-started-with-custom-connectors-using-remote-mcp) **[primary]**. OpenAI calls developer mode "powerful but dangerous" — [OpenAI developer mode](https://developers.openai.com/api/docs/guides/developer-mode) **[primary; snippet]**.
- Tool poisoning / rug pulls: hidden instructions in tool descriptions/schemas invisible in client UIs; "most clients don't diff tool definitions between sessions"; mitigations: version tool definitions, detect silent changes, pin/approve servers — [mcpservers.org security guide](https://blog.mcpservers.org/posts/mcp-security-best-practices), [practical-devsecops](https://www.practical-devsecops.com/mcp-security-best-practices/) **[secondary]**. An Aembit statistic ("only 18% of deployments scope tool permissions") could not be verified **[secondary; unverified]**.
- Claude Code redacts credential env vars in remote `url`/`headers` and only sends OAuth credentials to HTTPS/localhost token endpoints — [Claude Code MCP docs](https://code.claude.com/docs/en/mcp) **[primary]**.

### Inferences
- A shared memory server is a confused-deputy magnet: it will hold tokens for many users and clients. It must mint its *own* audience-bound tokens (own authorization server or a hosted one), never accept a client's upstream (Google/GitHub) token as authentication, and gate writes by the requesting principal's scopes (`memory:read`, `memory:write`, etc.).
- Because tool-result injection is the main threat to a memory store, memories returned to the model should be wrapped with provenance (source agent, source weight, timestamp) and the server should refuse to persist instructions-looking content without an explicit write tool call from a scoped principal; expose read-only tools with `readOnlyHint: true` so ChatGPT won't demand confirmation on reads, and mark destructive tools `destructiveHint: true`.

### Gaps
- Could not read the standalone "Security Best Practices" page (session hijacking, local server compromise); the normative items above are from the authorization and transport pages instead.
- No primary data on how clients detect/diff changed tool definitions ("rug pulls").

## Key Question 6: Pain points developers report in 2026 supporting many clients from one server

### Takeaway
The dominant 2026 problems are: (1) 2025-era session state breaking behind load balancers/serverless isolates (404 on `notifications/initialized`, which clients then mis-report as an SSE 405); (2) idle/long-lived SSE streams timing out or wedging servers in Cursor/JetBrains-class clients; (3) client-side SDK lag — most clients still send `initialize` with 2025-11-25, so servers must run dual-stack; (4) OAuth registration fragmentation (CIMD vs DCR vs static) causing some clients to be unable to connect at all; (5) ChatGPT-specific `search`/`fetch` expectations and `readOnlyHint`-driven confirmation; (6) the new mandatory `Mcp-Method`/`Mcp-Name` headers and the loss of a server→client back-channel.

### Cited Findings
- Issue #2187 (2026-10-04): with `@modelcontextprotocol/sdk` 1.30.0 the client "proposes 2025-11-25 in `initialize`," the server negotiates a 2025-06-18 session held "in an in-memory map on one isolate. If `initialize` lands on one isolate and `notifications/initialized` lands on another, the second returns 404. The client then retries over SSE, which sends a GET the server rejects with 405"; "The legacy protocol needs session affinity or shared session storage. The stateless 2026-07-28 revision needs neither" — [UsefulSoftwareCo/executor #2187](https://github.com/UsefulSoftwareCo/executor/issues/2187) **[secondary; issue tracker]**.
- Python SDK #520: "SSE sessions are created in one worker process, but subsequent requests may be routed to different worker processes, which yields 404s" — [python-sdk #520](https://github.com/modelcontextprotocol/python-sdk/issues/520) **[secondary; SDK tracker]**.
- JetBrains Junie: "Remote MCP server fails to connect: optional SSE listening stream times out after 10s" — [JUNIE-4021](https://youtrack.jetbrains.com/projects/JUNIE/issues/JUNIE-4021/Remote-MCP-server-fails-to-connect-optional-SSE-listening-stream-times-out-after-10s) **[secondary]**. Cursor: "HTTP MCP server becomes unresponsive after repeated SSE stream disconnects" — [Cursor forum](https://forum.cursor.com/t/http-mcp-server-becomes-unresponsive-after-repeated-sse-stream-disconnects/152243) **[secondary; unreachable]**.

- Single-instance servers: one `McpServer` connected per SSE connection locked out a second client; fix is one server instance per connection — [banjo #31](https://github.com/shatch/banjo/issues/31) **[secondary]**. ~15 agents sharing one stdio server exceeded a 60 s client timeout — [Vixl #167](https://github.com/jxburros/Vixl/issues/167) **[secondary]**.

### Inferences
